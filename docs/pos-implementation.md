# Offline POS implementation contract

The existing application is Flutter/Android, with Riverpod, editable local menu data and no cart or checkout. Existing browsing screens remain in place. A separate Order route supplies a cart, configuration and status workflow. The POS catalog is initialized from `lib/data/menu_data.dart` by `tools/export_catalog.dart`; a saved, previously edited menu is not silently treated as a POS price authority.

Implementation order: (1) catalog and native SQLite order engine; (2) Android foreground HTTPS service and private cashier method channel; (3) POS UI; (4) persistent menu cart, pairing and synchronization; (5) automated checks and deployment documentation.

Protocol: HTTPS on all IPv4 interfaces, port 8443 by default. Staff manually transcribes the full SHA-256 certificate fingerprint from POS to menu. Trust is restricted to that certificate, address and port, with validity dates checked; no global trust bypass. A six-digit setup code expires after five minutes and locks after five failed attempts, globally per window. Successful pairing consumes the code and returns a random device credential. Credentials authorize only catalog, submission and that device's individual orders. Approval/cancellation/history never have a network route; they use the POS activity's private platform channel. SQLite transactions commit before any success response. Polling every two seconds is the live-update equivalent: it also performs full authoritative reconciliation after disconnection, without event-loss gaps.

Order requests contain a random request ID and product IDs, integer quantities, allowed modifier IDs, notes and expected unit prices in centavos. Server catalog prices are authoritative; stale quoted prices are rejected for explicit review. SQLite enforces a unique `(device, requestId)` and a unique payment per order. Accepted order JSON snapshots names, modifiers and prices. Cashier decisions are terminal and include operator and time. Menu persists the complete frozen attempted request before sending, retains it across uncertain outcomes, and only retries that exact request. Ordinary carts never submit automatically.

Tradeoff: a native Android service avoids reliance on Flutter activity lifetime or a laptop. Two-second HTTPS polling is simpler and more recoverable than WebSockets at this two-tablet scale. Full fingerprint entry adds setup work but authenticates pairing without a cloud CA or a weak-code-only trust bootstrap. The POS is an unlocked physical cashier terminal; Android screen lock protects local authority, rather than distributing an administrator password.

Done means both Android APKs build, static analysis and available automated reliability checks pass, and remaining physical-tablet acceptance tests are explicitly recorded as unverified. No payment-provider integration is included.
